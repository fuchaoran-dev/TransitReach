# MD8-2 — Multi-stop Outing Pass and Plan Check

- **Parent:** Epic 8 extension for Epic 2
- **Priority:** Must Have
- **Status:** Planned; implementation is blocked until the Epic 2 multi-stop optimiser is complete.

## Purpose

> As a car-free resident of the Klang Valley
>
> I want my multi-stop outing checked and delivered as one pass
>
> So that I know when to leave, whether I can complete every stop, and what to change before I travel.

This document contains only the Epic 8 behaviour associated with the Epic 2 Trip Planner. It does not define the Epic 6 group invitation flow or the Epic 3 single-journey entry point.

## Dependencies

- Epic 2 supplies an ordered, recalculable multi-stop plan.
- Epic 4 supplies typical bus-delay information and explicit unsupported results.
- Epic 7 supplies forecast periods and walking-weather context.
- Essential Services supplies reliable opening hours where available.
- The shared Epic 8 pass renderer, storage and plan-check model should also be reusable by `MD8-6.md`.

The Epic 2 plan must expose stable stop and leg identifiers, visit durations, journey geometry, walking duration, planned connection times and an explicit recalculation operation. MD8-2 must not invent these values while Epic 2 is incomplete.

---

## US 8-2.1 — Check a Multi-stop Plan

> As a car-free resident
>
> I want every leg and visit in my outing checked
>
> So that I find the weak point before I leave.

### 8-2.1.1 Spare Time at Each Connection

Given an outing with more than one journey leg, When the check runs, Then every connection shows the estimated spare time between arriving and the next departure.

### 8-2.1.2 Typical Bus Delay Carried Forward

Given a bus leg on a route with delay history, When the check runs, Then the typical delay for that route, stop and hour is carried into every later connection, visit time and the estimated finish.

### 8-2.1.3 Opening Time at Every Stop

Given an outing stop has reliable opening hours, When the check runs, Then its estimated arrival, visit window and margin before closing are shown. A stop without reliable hours is labelled **“Hours unknown”**.

### 8-2.1.4 Weak Point Named

Given the check has run, When the result is shown, Then the tightest connection, closing-time margin or finish-time constraint is named in one sentence with the figures behind it. No single overall score is shown.

### 8-2.1.5 No Data Is Not “Fine”

Given a leg has no applicable delay history, When the result is shown, Then that leg is marked **“Not checked”** and looks different from a checked leg that passed.

### 8-2.1.6 Delay Evidence Is Applied Once

Given several checks refer to the same bus leg, When the timeline is recalculated, Then that leg's typical delay is applied once and its effect is propagated forward without double-counting.

## US 8-2.2 — The Multi-stop Pass

> As a car-free resident
>
> I want the checked outing as one compact pass
>
> So that I can follow the whole day at a glance.

### 8-2.2.1 Pass Contents

Given a checked outing, When the pass opens, Then it shows:

- when to leave;
- every journey leg in order;
- every outing stop in the planned order;
- the estimated arrival and visit window at each stop;
- the estimated finish; and
- the named weak point.

### 8-2.2.2 Times Are Estimates

Given any time on the pass, When it is displayed, Then it is worded as an estimate, such as **“Leave around 5:40 pm”**, and never as a guaranteed scheduled departure.

### 8-2.2.3 Weather on the Pass

Given a forecast is available for the outing, When the pass opens, Then it shows each relevant forecast period, the source and the total walking time that falls within each period.

### 8-2.2.4 Canonical Pass Format

Given a multi-stop outing is converted into a pass, Then it uses the shared Epic 8 pass structure rather than an Epic 2-specific visual format. Multi-stop visits are represented as repeated stop sections inside that structure.

## US 8-2.3 — The Solo Letter

> As a car-free resident
>
> I want a clear hand-off from planning to travelling
>
> So that I know the outing is ready to use.

### 8-2.3.1 Get Pass

Given the user has a valid recalculable outing in the Trip Planner, When they select **“Get pass”**, Then a letter titled **“Your outing is ready”** appears.

### 8-2.3.2 Open the Letter

Given the letter is visible, When the user opens it, Then it opens the checked pass for the current version of the outing.

### 8-2.3.3 Incomplete Plans Stay in the Planner

Given Epic 2 cannot produce a complete ordered plan, When the user attempts to get a pass, Then no ready letter is shown and the planner identifies what must be completed first.

## US 8-2.4 — Keep It and Find It Again

> As a car-free resident
>
> I want to save my outing pass and return to it later
>
> So that I do not have to plan the outing again.

### 8-2.4.1 Download

Given a pass is open, When the user selects **“Download”**, Then an image is saved containing the leave time, ordered stops, journey legs, estimated finish and weak point, readable without an internet connection.

### 8-2.4.2 QR Code

Given a pass is open or downloaded, When its QR code is scanned, Then the corresponding live pass opens with its map and walking directions.

The QR code must use an opaque pass reference or URL. It must not directly encode the user's starting point, full itinerary or other private plan data.

### 8-2.4.3 My Passes

Given the user has produced one or more passes, When they open **“My passes”** on the same device, Then each upcoming pass is listed and can be reopened.

### 8-2.4.4 Re-check on Reopening

Given a pass is reopened before the outing, When newer forecast or delay information is available, Then the plan check runs again and the pass states whether the plan still holds.

The last successfully checked result may remain visible while refreshing, but it must be labelled with its check time and must not be presented as current after the underlying plan changes.

---

## US 8-2.5 — Fix It and Carry On

> As a car-free resident
>
> I want to act on the weak point from the pass
>
> So that the check produces a better outing rather than only a warning.

### 8-2.5.1 Suggested Fix

Given a weak point is named, When a supported fix exists, Then the pass offers one or more applicable actions:

- leave earlier;
- change the order of stops; or
- choose another outing time.

An action must return its constraint to Epic 2 and request a new optimiser result; the pass must not edit calculated times in place.

### 8-2.5.2 Re-check After a Change

Given the user applies a fix or changes the outing, When Epic 2 produces the replacement plan, Then the check runs again and the pass is replaced with the new plan version.

### 8-2.5.3 Add Errands to a Group Outing

Given a member opens **“Add errands”** from an `MD8-6` group pass, When the Trip Planner opens, Then the confirmed meeting place and agreed time are fixed constraints and the member may add private stops around them.

This is a cross-epic integration criterion. It remains blocked until both MD8-2 and MD8-6 are available. The added errands, route and starting point are private to that member.

## Out of Scope

- Completing or substituting for the Epic 2 optimiser.
- Group invitation, room confirmation and group arrival-status UI; these belong to `MD8-6.md`.
- Showing one member's private errands, route or starting point to other group members.
- Presenting forecast or historical-delay estimates as guaranteed operating information.
